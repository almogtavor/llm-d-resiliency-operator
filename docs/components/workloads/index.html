Workload

The workload owns the Pods of one engine group. It does four things:

  • reports the group's Pods as they are right now,
  • resets Pods: replaces each named Pod with a new Pod in the same place, while the rest of the group keeps running,
  • resets all: recreates the whole group,
  • releases Pods: removes them and frees their GPUs. It never adds Pods.

It remembers nothing: no earlier calls, no earlier groups. Deciding whether this is still the same group is the controller's job. It knows nothing about engines beyond which of its containers run one, which is configuration: no ranks, ports or processes. The first implementation, LWS, comes with its own PR and doc.

Interface​

type Workload interface {
    Discover(ctx context.Context) (Group, error)
    Reset(ctx context.Context, pods []PodRef) error
    ResetAll(ctx context.Context, pods []PodRef) error
    Release(ctx context.Context, pods []PodRef) error
}

Objects​

// Group is the group as it is now.
type Group struct {
    Pods            []Pod // every Pod, sorted by Index, including starting and terminating ones
    Recreating      bool  // the workload is replacing the whole group right now
    RecreateStopped bool  // the workload gave up recreating the group, e.g. its restart budget is used up
}

// Pod is one Pod of the group.
type Pod struct {
    Name     string
    UID      string
    IP       string
    Index    int      // position in the group, fixed for the Pod's life
    Identity string   // UID + the engine containers' IDs and restart counts. Changes while the Pod starts, then only when it is replaced or an engine container restarts.
    Node     string   // the node it runs on, empty until scheduled
    State    PodState
}

type PodState string

const (
    PodStarting    PodState = "Starting"    // scheduling, pulling, or containers not all running yet
    PodReady       PodState = "Ready"       // every container runs and the Pod has an IP
    PodTerminating PodState = "Terminating" // being deleted
)

// PodRef names one Pod. The UID makes it exact: a new Pod with the same name is a different Pod.
type PodRef struct {
    Name string
    UID  string
}

// ErrUnsupported means the workload cannot do this at all. Nothing was changed.
var ErrUnsupported = errors.New("unsupported")

Functions​

Discover​

Reports the group as it is now.

Inputnone
OutputGroup, or an error
Errorsonly when the workload cannot be read, or its spec is not supported. Starting, terminating and missing Pods are facts, not errors.
Side effectsnone

Example, while pod-3 is reset in a member dies:

Recreating: false
RecreateStopped: false
Pods:
- {Name: pod-0,   UID: a1, Index: 0, Identity: idA,  Node: gpu-node-1, State: Ready}
- {Name: pod-1, UID: b1, Index: 1, Identity: idB,  Node: gpu-node-2, State: Ready}
- {Name: pod-2, UID: c1, Index: 2, Identity: idC,  Node: gpu-node-3, State: Ready}
- {Name: pod-3, UID: d2, Index: 3, Identity: idD2, Node: gpu-node-9, State: Starting}

pod-3 has a new UID: it is a new Pod in the same place. Discover does not say that the old one was reset on purpose. The controller knows that from its journal.

Reset​

Replaces each named Pod with a new Pod in the same place. The rest of the group keeps running.

Inputpods []PodRef: the Pods to replace, as the controller last saw them
Outputnil once every replacement is triggered, or once none of the named Pods (by UID) exist. ErrUnsupported when the workload cannot replace one of them without recreating the group: it decides that before touching any Pod, and changes none of them. Another error otherwise.
Side effectseach named Pod goes. A new Pod with the same Index and a new UID starts in its place. The replacements start on their own and may become Ready at different times.

Example.

Reset(ctx, []PodRef{{"pod-2", "c1"}, {"pod-3", "d1"}})
// a workload that supports it: both are deleted and come back with new UIDs. Returns nil.
// the same call again: no named Pod exists. Returns nil, changes nothing.
// the list names a Pod the workload cannot replace alone, such as its leader: ErrUnsupported, changes nothing.

ResetAll​

Recreates the group that the named Pods belong to.

Inputpods []PodRef: the Pods of the group to recreate, as the controller last saw them
Outputnil once the recreation is triggered, or once none of the named Pods exist. An error otherwise.
Side effectsthe whole group is replaced by new Pods, when the workload's own restart policy allows it

Example.

ResetAll(ctx, []PodRef{{"pod-0", "a1"}, {"pod-1", "b1"}, {"pod-2", "c1"}, {"pod-3", "d1"}})
// first call: the workload deletes pod-0 (UID a1), and the whole group is recreated. Returns nil.
// after the new group exists: pod-0 now has UID f1, so no named Pod exists. Returns nil, changes nothing.

The second call is why the controller can repeat ResetAll until the old Pods are gone: it can never touch the new group.

Release​

Removes the named Pods and frees their GPUs. Nothing is added in their place.

Inputpods []PodRef: the Pods to remove
Outputnil once the removal is triggered, or once none of the named Pods exist. ErrUnsupported when the workload cannot remove Pods from a running group, with nothing changed. Another error otherwise.
Side effectsthe named Pods go, and the group gets smaller

Example.

Release(ctx, []PodRef{{"pod-3", "d1"}})
// a workload that supports it: pod-3 starts terminating and is not replaced. Returns nil.
// the same call again: no Pod with UID d1 exists. Returns nil, changes nothing.
// a workload that cannot: returns ErrUnsupported, changes nothing.

Rules​

RuleWhy
No memory. Every answer comes from the cluster as it is now.a restarted IRO or a new leader gets the same answers
Discover fails only when it cannot read the workload, or its spec is not supportedthe controller should see starting and terminating Pods, not lose sight of the group
Pods are sorted by Index, and a Pod keeps its Index for lifestable addressing for the engine driver
Once its engine containers run, Pod.Identity changes only when the Pod is replaced or an engine container restartsa restarted engine is never mistaken for the old one, and a sidecar restart does not look like lost members
Reset, ResetAll and Release take a list and touch only the Pods they name, by UIDa late call can never hit a new Pod
All three can be repeated: once the named Pods are gone, they do nothingthe controller repeats them until Discover shows the result
Reset never recreates the rest of the group. If it would have to, it returns ErrUnsupported.the healthy members keep serving
Release never adds a Podcapacity comes back only through a reset
A workload that cannot do something changes nothing and returns ErrUnsupported. For a list, that is all or nothing.the controller asks for each Pod alone, and keeps the ones the workload cannot handle as they are
No engine knowledge: ranks, ports, processes, endpointsthat belongs to the engine driver

Considerations​

  • Who paces resets. The workload paces recreations and decides when to stop, including ones IRO asks for. IRO has no reset budget of its own. A workload that stopped says so in RecreateStopped.
  • Same place, maybe not the same node. Reset keeps the Pod's Index, but the scheduler may put the new Pod on the same node. If the node is the problem, the new Pod fails too, the join fails, and the group serves with fewer members until the next group. Moving work off a bad node is outside this contract.
  • Leaders. Some workloads cannot replace or remove their leader without recreating the group. They return ErrUnsupported for any Reset or Release that names it. The controller then asks for the other Pods alone, and keeps the leader as it is.
  • Several Pods are not a recreation. Reset and Release never name every Pod of the group: the controller names only Pods whose members a reconfig removed, and some members always stay. Replacing the whole group is ResetAll.
  • Report Recreating as early as possible. A workload that will recreate the group because of what it sees (for example, any container restart, when its policy recreates the group for that) reports Recreating right away, not only once the leader is deleted. Otherwise the controller may plan a reconfig for a group that is about to go.
  • Recreating vs. stopped. Recreating is temporary: the controller waits. RecreateStopped is the workload saying it gave up: the controller waits too, and telemetry reports it.
  • Engine containers. The workload must know which containers run the engine. If it also counts a sidecar, a sidecar restart looks like an engine restart: the members are lost and their new IDs serve without being admitted, which breaks C5 and resets the group. If it leaves an engine container out, a restarted engine passes for the old process. Recreating is different: it predicts what the workload itself will do, so it follows the workload's own restart policy, which may count every container.

Later: disaggregated sets​

A prefill/decode set holds several engine groups with different roles. Proposal: each engine group is one recovery unit with its own Group, journal record and controller loop, and the workload lists the units. This is open decision 1 in the overview.
