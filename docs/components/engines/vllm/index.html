vLLM engine

How vLLM implements the engine contract, on top of the vLLM fault tolerance API from vllm-project/vllm#46370. Code: internal/engine/vllm.

What vLLM gives​

Each data parallel rank runs its own API server (external load balancing, --data-parallel-size-local 1). On --enable-fault-tolerance, a rank that hits a fault stops serving and waits for an instruction:

EndpointUse
GET /v1/fault_tolerance/statusstatus, fault_info, mask, and for the last instruction ft_state, last_ft_request_id, ft_error
POST /v1/fault_tolerance/applyretry or scale_down; 202 means queued, and the result, including a refusal, shows in the status
GET /health503 once the engine process is gone

Rules that shape the driver:

  • An instruction is accepted only while the rank is unhealthy.
  • Every alive rank must get the same request_id within 10 seconds, or the reconfig fails.
  • scale_down keeps the original rank numbers. Removing the lowest alive rank also moves the store it hosts, so the request carries the next lowest rank's address and a port.
  • A failed scale_down is final: the ranks report dead.
  • The status is cached by the API server. If the engine process is killed, it can still say healthy; /health is what notices.

Deploying vLLM for IRO​

  • Set VLLM_KEEP_ALIVE_ON_ENGINE_DEATH=1. Otherwise the API server exits with its engine and its container restarts: under RecreateGroupOnPodRestart the workload recreates the whole group and IRO never gets to shrink it; under None IRO removes the rank only once the restart changes its Pod's identity, and the restarted rank cannot rejoin.
  • No liveness probe on vLLM containers. A probe on the status or on a completion fails on every rank paused for recovery, and the restart loses that rank: under RecreateGroupOnPodRestart the group is recreated; under None the rank is removed with the dead one, or the reconfig in flight fails and the group is reset. A restarted rank never rejoins and holds its GPU until the next group. Under None, GET /health is the only safe target: it stays 200 while a rank is paused and turns 503 only when the engine process is gone.
  • With sidecars in the Pod, name the vLLM container in --lws-engine-containers, and point --vllm-api-port at vLLM's own port, not a proxy's.
  • /health stays 200 for a rank that is dead while its engine process lives, so a /health readiness probe keeps sending traffic to it, and it answers 503. Readiness that routes well checks the status endpoint for healthy.
  • engine_recovery_timeout_sec must leave room for detection plus IRO's diagnosis deadline.
  • scale_down needs EPLB with redundant experts and an all2all backend with timeouts (nixl_ep or deepep_low_latency).
  • Size the redundant experts for the ranks you want to lose in place: the survivors' slots must hold every logical expert. With E experts, R redundant and N ranks, losing k ranks needs (N - k)(E + R)/N >= E. Otherwise the reconfig fails ("no redundant slot for missing expert") and the group is reset.
  • nixl_ep from NIXL 1.4 on uses GPU-initiated RDMA across Pods. Restrict UCX_NET_DEVICES to the RDMA devices the Pod can use for GPU memory, and make sure the nodes support it; within one Pod it runs over NVLink.

Known engine issues​

Found with vllm#46370 (384ba19, then fcfbd37) on two setups: 4 H200 Pods of one rank each over InfiniBand (DeepSeek-V2-Lite, nixl_ep from NIXL 1.3.2), and one Pod of 4 H100 ranks over NVLink (Qwen3-30B-A3B, NIXL 1.3.2 and 1.5.0).
