Controller

The controller runs one loop per engine group, on the elected leader. Every poll it reads the workload and the engine, decides what the group needs, and acts. It owns everything that is not engine- or workload-specific:

  • the phases and their deadlines,
  • whether it is still the same group,
  • connecting Pods to engine members,
  • saving state in the journal before acting,
  • resets, and bringing capacity back after a shrink,
  • the checks every engine plan must pass.

It reads only the engine-neutral Member fields and Pod facts. Everything engine-specific stays in the engine.

Interface​

func New(ctx context.Context, workload Workload, engine Engine, journal Journal, recorder Recorder, config Config) (Controller, error)

type Controller interface {
    Step(ctx context.Context) error
}

A runner calls New until the journal loads, then Step every PollInterval while this process leads. When Step returns ErrConflict, the runner drops the controller and calls New again. New and the defaults below come with the implementation; the code defines Controller and its objects.

Objects​

// Config holds the controller's settings. Flags are in Configuration below.
type Config struct {
    PollInterval     time.Duration   // 1s
    DiagnosisTimeout time.Duration   // 75s: longest time in recovering without a reconfig
    ApplyTimeout     time.Duration   // 90s: longest time a reconfig may stay in flight
    VerifyTimeout    time.Duration   // 2m: how long a failed check after a reconfig is retried
    UnseenTimeout    time.Duration   // 10m: longest time no admitted member can be read before the group is reset
    FlapWindow       time.Duration   // 2m: check C6
    CapacityRestore  CapacityRestore // reset-pod (default) | reset-all | release
}

type Phase string // starting | serving | recovering

// CapacityRestore says how capacity comes back after a shrink.
type CapacityRestore string // reset-pod | reset-all | release

type MemberState string // candidate | admitted | excluded | rejected

// PodRecord is what the controller remembers about one Pod.
type PodRecord struct {
    Name     string
    Identity string
    Node     string // so an incident can name the node of a Pod that is already gone
    Removing bool   // asked to go, through Reset, ResetAll or Release
}

// Record is the controller's whole state. It is what the journal stores.
type Record struct {
    Phase  Phase
    Since  time.Time // when the phase started. The diagnosis deadline counts from here.
    Reason string

    Pods    map[string]PodRecord // by UID. Also what ResetAll names.
    Members map[MemberID]MemberState

    Reconfig      *Reconfig  // in flight, nil when none
    ReconfigSince time.Time  // the apply deadline counts from here
    Acceptances   []Acceptance
    Verifying     []MemberID // members of a reconfig that succeeded, not yet checked with Verify

    LastNoChangeReconfig time.Time // check C6
    VerifyFailedSince    time.Time
    UnseenSince          time.Time // Discover failed, or Observe read no admitted member. Deadlines do not count this time.
    RecreateStopped      bool      // from the last Discover, so people can see the workload gave up

    Incident *Incident // the open incident, nil when none. Closed ones go to telemetry.
}

Reconfig, Acceptance and MemberID come from the engine. Incident comes from telemetry.

Functions​

New​

Builds the controller and loads its state.

Inputa Workload, an Engine, a Journal, a Recorder, a Config
Outputa Controller, or an error
Side effectsJournal.Load

Examples.

New(...) // empty journal (first run):       Record{Phase: starting}
New(...) // leader changed during a reconfig:   Record{Phase: recovering, Reconfig: iro-ft-7c1e, ...}. The next Step watches Progress. It sends the reconfig again only if no acceptances were saved and Progress says NotStarted.
New(...) // journal unreadable or not valid: error. The runner logs it and calls New again next poll.
New(...) // after a save conflicted: Record as saved by the other writer. Deadlines restart, as after a leader change.
New(...) // the record was deleted while running: the last save conflicted, and now the journal is empty: starting.
New(...) // a phase this version does not know: starts over, as with an empty journal.

Step​

Runs one reconciliation: read, decide, act.

Inputnone
Outputnil, or an error that the runner logs. An error before a save leaves the saved state as it was. A workload call that fails after its save is repeated on the next poll, and its error is returned once the step has saved.
Side effectsany of Journal.Save, Probe, Apply, Verify, Reset, ResetAll, Release, and Recorder calls for what happened

In order:

  1. Discover. If it fails, the controller cannot see the group: keep the phase, pause its deadlines, note the time, and stop here.
  2. Read Discover against the journal: same group, new group, or going away. While the old group is going, repeat any owed ResetAll and stop here. See Reading Discover.
  3. If starting, record the Pods, Observe, and ask for a Plan over the members that are not Terminal. Wait while a Pod is Starting or gives no members. On a Healthy plan, admit every member and go to serving. Stop here: no member is admitted yet, so there is nothing to check.
  4. Observe the Pods and connect members to Pods. If it reads none of the admitted members, stop here as in step 1, or reset the group once that has lasted UnseenTimeout. See unknown members.
  5. Check the observation (C1, C4, C5). A violation resets the group. Unknown members are not checked.
  6. Act by phase. Ask the policy for a Plan, or for Progress when a reconfig is in flight. Check and send a new reconfig, verify the members of a reconfig that succeeded, or reset.
  7. Restore capacity if the group is serving.

Behavior​

State machine​

The controller is always in one of three states. There is no final state: it never gives up on a group.

StateMeaningThe controller
startingthe group is coming up: a new group, or one that was just resetwaits for every member, then admits them all. No deadline: how fast the group comes up is the workload's call.
servingthe group serves, maybe with fewer members than it started withchecks the result of a recovery it just made, and brings failed Pods back
recoveringthe engine reports a faultremoves dead members in place with a reconfig, or retries
FromToWhen
startingservingevery member is up: the policy says Healthy
servingrecoveringthe engine reports a fault: the policy says anything but Healthy, other than adding members back
recoveringservingthe fault is repaired: the policy says Healthy, or the reconfig succeeded
serving or recoveringstartingrecovery in place cannot help, so IRO resets the group (ResetAll). Each failure says when.

Details per state:

  • starting: while Pods of the old group remain, the controller repeats the ResetAll and does nothing else (see Reading Discover). Then it records the Pods every poll and ignores any plan but Healthy.
  • serving: plans every poll. A plan that only adds members runs a reconfig here too, to admit the members of a Pod that was reset.
  • recovering: probes once on entry, and sends a reconfig no sooner than 2 polls in. Resets on Unrecoverable. While a reconfig runs, it follows Progress instead of planning.

Reading Discover​

The workload only reports Pods as they are now. The controller decides what they mean by comparing them with the Pods saved in its journal.

Pod compared with the journalMeaningController does
saved, same identity, not Terminatingunchangednothing
saved as Removing, now gone or Terminatingthe Reset or Release is happeningforgets it once it is gone
saved, not Removing, now gone or Terminatingits members are lostadds them to the observation as Terminal (lost members), so the policy plans as usual and a reconfig can remove them
saved, not Removing, same UID with a new identity: an engine container restarted in placeits members are lost. The restarted container's members are not in the group.the same for the old members. It keeps the Pod's old identity while it tracks them, so once a reconfig removed them the Pod is restored like a failed Pod. The new members are never candidates. A Pod that restarts before its members were recorded is only a slower start.
not saved, Startinga replacement Pod is loadingsaves it and waits
not saved, Readya replacement Pod is upits members, as Observe reports them, are candidates

A ResetAll is owed when every saved Pod is Removing. Once none of them remain, the first check fails, the second finds no saved Pod, and the new Pods form a new group.

While starting, every Pod belongs to the group being started. The controller records the Pods again on every poll and does not connect or check members. On the first Healthy plan it admits every member it saw. The table above, connecting Pods and members and checks C1, C4 and C5 apply from then on. An empty journal (IRO's first run) is a new group.

Connecting Pods and members​

Discover reports Pods. Observe reports members, each with the Pod it runs on. The controller joins the two by Member.ID() (m3@idD) and keeps each ID as candidate, admitted, excluded or rejected. Excluded means a reconfig removed it, and its Pod may still be reset. Rejected means it stays out until the next group: a candidate that could not join, or an excluded member whose Pod is kept as it is.

CaseController does
member reported on a saved Podmatches it by ID
member reported on a new, Ready Podrecords it as a candidate
admitted member reported Unknown, or not reported while its Pod is unchangedunknown: see unknown members
admitted member on a Pod that is gone, Terminating or has a new identity (replaced, or its engine restarted)lost: added to the observation as Terminal, Detail: "pod lost"
member reported under a restarted Pod's new identitynot tracked, never a candidate. C5 still applies: it must not serve.

Unknown members​

An unknown member is one IRO cannot read now: it is never Serving, never Terminal, and never put in Remove by a new plan. What happens depends on how many admitted members IRO can read. Lost members do not count as read.

Admitted members IRO can readController does
all that are not lostas usual
some, and others are unknownthe group is not healthy: a Healthy plan, or a grow in serving, counts as a fault. A Change that passes the checks but names an unknown participant is not sent: the controller waits. If they stay unknown, the diagnosis deadline resets the group, which is what stops them.
none, and some are unknown (the rest lost)it cannot see the group, as when Discover fails: no incident, no plan, and its deadlines are paused. If that lasts UnseenTimeout, counted from UnseenSince, the group is reset (reason unseen): a hung frontend, or every member hung, is not left alone forever.

An unknown member never becomes Terminal by timeout. IRO cannot tell a hung member from one only IRO cannot reach, and the router may still send it traffic: removing it would break C1. Only the engine (Terminal) or the workload (the Pod is gone, Terminating or restarted) proves a process is gone.

Step by step: IRO cannot see the group.

Reconfigs​

A reconfig is the one engine action IRO can have in flight. It is saved in the journal before it is sent, and cleared when Progress reports Succeeded or Failed.

No reconfig in flightReconfig in flight
Asks the policyPlanProgress
DeadlineDiagnosisTimeout, from the faultApplyTimeout, from ReconfigSince
Members in Removeadmittedstill fenced: they must reach Terminal (C1, C4)
After a leader changeplans againwatches Progress. Sends the same reconfig again only if no acceptances were saved and Progress says NotStarted.

The two deadlines catch different hangs: an engine that never reaches a state IRO can act on, and a reconfig that never finishes. While the workload reports Recreating, deadlines are not checked, and both restart when it ends, and when a new leader takes over. While the controller cannot see the group, deadlines do not count either: when it sees the group again, Since (in recovering), ReconfigSince and VerifyFailedSince move forward by the time it could not see. A new group drops the reconfig in flight: the workload is already replacing everything.

A reconfig that never left. The reconfig is saved before Apply, and its acceptances after. No saved acceptances means the send was never confirmed: the leader may have died before Apply reached the engine. When Progress then says NotStarted, the controller checks the reconfig again (C1 to C3, and C7 on the current observation), saves, and sends the same reconfig: same ID, same members. A reconfig that no longer passes is dropped, since nothing reached the engine, and the controller plans again. A resend restarts ReconfigSince and is not a new reconfig for C6. With acceptances saved, NotStarted counts as Running. An engine that cannot prove that no member got a reconfig never says NotStarted: the reconfig then fails, or runs into its deadline, and the group is reset.

After a reconfig succeeds, the controller saves its participants and joiners in Verifying and calls Verify on them every poll until it passes. Members the reconfig removed are already out and are not checked. One failed request is not a fault: a failure is retried for VerifyTimeout, and only a member that still cannot generate after that resets the group (reason verify_failed, naming every member that failed). If the engine reports a fault meanwhile, or a member becomes unknown, the group goes to recovering, where the policy can remove a dead member in place. The check is kept: when the group serves again it resumes, and the incident stays open until it passes, unless a new reconfig succeeds and replaces it. While IRO cannot see the group, the retry window is paused like the deadlines. A new leader finds Verifying in the journal and continues the check. Verify runs only here: IRO checks what it changed, nothing else. A fresh group, or one that recovered without a reconfig, goes to serving on a Healthy plan.

Step by step: the IRO leader dies mid-reconfig, a reconfig fails.

Restoring capacity​

Capacity never comes from new Pods. It comes back by resetting the failed Pod, or the whole group. This runs only while the group is serving; a fault comes first.

  1. Once the members of the last reconfig passed Verify, on a poll whose plan is Healthy, the controller looks for Pods that hold only excluded members. It marks them all Removing, saves once, and names them all in one Reset, ResetAll or Release, per --ft-capacity-restore (C8). If a call that names several Pods returns ErrUnsupported, it asks for each Pod alone, so a Pod the workload can never replace does not keep the others below full. A Pod that is already gone is just forgotten. A Pod restarted in place is one of them once the reconfig that removed its old members finished.
  2. After a Reset, the new Pods start on their own. Their members become candidates as each Pod becomes Ready, and the policy admits them in ordinary reconfigs: one for all of them, or one as each is ready.
  3. There is one try, no budget. If the Pod cannot be reset (ErrUnsupported, or the engine cannot grow), or the new Pod's members are rejected (the join reconfig fails, or the new Pod restarts before joining), the group keeps serving with fewer members. The Pod's members are marked rejected, so it is not tried again. A new Pod that is still starting is waited for.
  4. With release, the released Pod goes and the group serves with fewer members. ErrUnsupported keeps the Pod as it is, the same way.
  5. With reset-all, any excluded or rejected member resets the whole group (reason capacity), even when its Pod still holds admitted members, so the group never stays below full.
  6. Other workload errors are not failures: the call is repeated on the next poll.
  7. Full capacity comes back with the next group: any ResetAll, or a recreation by the workload.
  8. There is no extra state: the Removing Pods, the member states and the reconfig in flight say where things are.

Step by step: several members die at once.

Rules​

Checks on every plan​

The policy decides. The controller still refuses any plan that breaks these rules, so a wrong policy can stall or reset a group but cannot exclude a member that still serves.

#RuleWhy
C1Remove holds only members that are Terminal when the plan is checked: an unknown one fails. They stay Terminal until the reconfig succeeds; one that later reads unknown is not checked.the router follows native health. A removed member that still serves gets traffic outside the group.
C2Add holds only candidates that are Joinable, on Pods that are Ready and unchangeda stale Pod must not join
C3Participants and Remove are admitted members, Add holds candidates, the three are disjoint, and Participants is not emptya reconfig must name a real, consistent membership change
C4Excluded members stay Terminal. An unknown one is not checked: it cannot serve.otherwise an excluded member could take traffic again
C5Members that are not admitted are not Serving, except those the reconfig in flight addsa joiner must not take traffic before it is in the group
C6A reconfig that changes no membership cannot repeat within FlapWindowstops retry loops
C7One reconfig at a time. Every member a reconfig names is in the observation it is planned on, lost members included. Apply refuses any other reconfig.a stale reconfig cannot apply to a changed group
C8Reset and Release name only Pods whose every member is excluded, after the reconfig that removed them finishedthe engine must no longer depend on a Pod before it goes

A plan that fails C1 to C3 resets the group. An observation that fails C1, C4 or C5 resets the group. The observation is checked in serving and recovering. In starting no member is admitted yet: the Healthy plan that ends starting admits them all. C8 limits what the controller itself sends, so it is never violated at runtime.

Step by step: a transient fault.

Considerations​

  • IRO cannot see the group. A failed Discover, or an Observe that reads no admitted member, proves nothing about the group: IRO may be the one cut off. The controller keeps the phase, opens no incident, asks for no plan, and pauses its deadlines. A group whose every member hangs, or whose single frontend hangs, looks the same, so the wait is bounded: once no admitted member has been readable for UnseenTimeout, the group is reset. The timeout is long, so a short blip on IRO's side never resets a group that serves. A failed Discover never resets: IRO cannot see the Pods it would name. A real fault does not wait that long either: an engine that gives up on recovery reports its members Terminal, and the group is reset once IRO sees it again.
  • The workload gave up. RecreateStopped makes the controller wait and act on nothing. Telemetry reports it so people can see it. Recovery resumes when the workload recreates the group.
  • Why verify only after a reconfig. Verify does not gate traffic: the router follows the engine's native health. Its job is to catch a recovery the engine reports as done but that cannot generate. That risk comes from what IRO changed, so that is when it checks. One slow completion is not a fault, so a failure is retried for VerifyTimeout before the reset.
  • Why a failed check resets the whole group. It happens only when the engine reports every checked member Serving and one still cannot generate after VerifyTimeout. The checked members are admitted and the engine depends on them: after a shrink or a retry they are every member left, and in expert parallel every member takes part in every step. No smaller action is safe. A reconfig removes only Terminal members (C1), and a Pod is reset only once the engine no longer depends on it (C8). Resetting the failing member's Pod would be a new fault for every member that shares a step with it, and its replacement comes back only if the engine can grow. Keeping the member admitted is not safe either: the router keeps sending it traffic that fails. --ft-capacity-restore does not apply: it is about Pods whose members a reconfig already removed.
  • No give-up state. IRO resets whenever recovery in place cannot help. How often a group may be recreated, and when to stop, is the workload's restart policy (for LWS, restartBackoff and maxGroupRestarts).
  • Restarts in place. Kubelet restarts a crashed or probe-failed container without replacing its Pod. A workload that recreates the group for that reports Recreating, and the controller waits for the new group. One that does not (for example LWS with restartPolicy: None) reports the same UID with a new identity, and the controller handles it like a lost Pod: a reconfig removes the old members, and capacity comes back only through the Pod's reset. The restarted container's members are never candidates: IRO did not ask for them, and a container that restarted once may restart again, so the fresh Pod from Reset is the one try. A restart during recovery costs more: a member paused for a reconfig that is restarted is lost too, so it is removed with the dead one, or the reconfig in flight fails and the group is reset. Probes on engine containers must not fail while a member is paused for recovery; each engine doc names the probes that are safe, if any.
  • Why the controller decides "same group". It already remembers which Pods it asked to reset or release, so it can tell those from a lost one. The workload stays a plain reporter.
  • Why reset the failed Pods first. It is the smallest action that brings capacity back: only the failed Pods restart, and the other members keep serving. ResetAll stops the whole group while the model loads again, and when this group is the only one serving the model, that is a full outage. So when a Pod cannot come back, the default keeps serving with fewer members. --ft-capacity-restore=reset-all takes the outage to get back to full.
